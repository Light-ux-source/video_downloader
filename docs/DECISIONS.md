# 技术决策记录（ADR）

记录项目中的关键取舍。格式：**背景 → 决策 → 理由 → 代价**。

---

## D1. Python 运行时方案

**背景**
目标机器只有系统自带 **Python 3.9.6**（无 brew python、无 conda），
而 yt-dlp 的 Python 包要求 **≥3.10**。同时需要保证"别人 clone 下来也能一把跑起来"。

**决策**
`setup.sh` 下载官方 python.org 的 **Python 3.12 安装包**，用 `pkgutil --expand-full`
**就地解包**到项目内 `runtime/`，再由 `run.sh` 设置
`DYLD_FRAMEWORK_PATH` / `DYLD_FALLBACK_LIBRARY_PATH` / `SSL_CERT_FILE` 后使用。

**理由**
- 不需要 sudo，不写系统目录（对比：直接装 pkg / `brew install` 都要动系统）
- 卸载 = 删 `runtime/` 目录，零残留
- 不依赖系统 Python 版本，可随项目升级

**代价**
- `runtime/` 约 243MB，不能入库（已 gitignore），首次 `setup.sh` 需下载约 45MB
- macOS 专属方案（Windows/Linux 需换 python-build-standalone 或系统包管理器）

**曾踩的坑**：framework 里的 `python3` **直接执行会 Abort**（dyld 找不到依赖），
所以探活必须通过 `run.sh`，否则会被误判为"运行时缺失"并触发重新解包，
甚至在解包失败时把可用运行时删掉。现已改为"先校验、后替换"。

## D2. 用 PyPI 包而非官方单文件二进制

**背景**
最初方案是使用 yt-dlp 的官方 GitHub Release 单文件二进制（最简单、无依赖）。

**决策**
改为从 **PyPI 镜像**安装 `yt-dlp[default]` 到自带运行时里。

**理由**
实测本网络环境下 `github.com/.../releases/download/...` **302 后对象存储不可达**
（多次重试、镜像站也全部失败），而 PyPI 镜像（USTC/清华/npmmirror）速度很好。

**代价**
- 引擎与 Python 运行时绑定（升级引擎要重跑 `setup.sh`）
- 好处是仍保持"独立进程调用"，业务代码不受影响

---

## D3. 把 yt-dlp 当进程而不是库

**决策**
`core/ytdlp.py` 全部通过 `subprocess` 调用 `python -m yt_dlp`，不 `import yt_dlp`。

**理由**
- 升级引擎 = 换包，不需要改/重启业务代码
- 出问题可直接在命令行复现（`./run.sh -m yt_dlp ...`），排障成本低
- 进程级取消简单可靠（进程组 SIGTERM → SIGKILL）
- 避免 yt-dlp 的异常体系与我们的错误处理耦合

**代价**
- 需要解析文本输出（进度、阶段、产物路径），比用 API 回调脆弱
- 已用"按结构识别而非按前缀"+"三级兜底定位产物"来对冲

---

## D4. 后端只用标准库

**决策**
HTTP 层用 `http.server.ThreadingHTTPServer`，不引入 FastAPI/Flask。

**理由**
- 零第三方依赖 → 环境问题少一个数量级
- 目标机器的 Python 版本不可控，少一层版本兼容风险
- 本项目接口数量有限（10 个），手写路由完全可控

**代价**
- 没有自动文档、参数校验、中间件生态（已用 `docs/API.md` + 手写校验弥补）
- 若要扩展成多用户服务，需换成成熟框架（架构上已隔离在 `core/server.py`）

---

## D5. SSE 而非 WebSocket / 轮询

**决策**
进度推送用 Server-Sent Events。

**理由**
- 单向推送场景，SSE 语义刚好
- 浏览器原生 `EventSource`，自带断线重连
- 比轮询省资源，比 WebSocket 少一套握手/心跳/状态管理

**代价**
- 每个任务一条长连接（浏览器对同域连接数有限制），因此终态必须及时关闭
- 已配合：终态关闭 + `end` 事件 + 20 秒兜底轮询

## D6. 前端产物入库

**决策**
`static/`（Vite 构建产物）提交进仓库，`.gitignore` 里注释掉忽略规则。

**理由**
- clone 后**不需要 `npm install`**（36MB 依赖 + 网络）即可使用
- 与"零门槛跑起来"的整体目标一致

**代价**
- 改前端必须记得 `npm run build` 并提交产物，否则仓库里的页面是旧的
- 产物与源码可能不同步（缓解：README 与开发文档都明确提示）

## D7. 不引入数据库

**决策**
任务状态保存在内存（`TaskManager.tasks`），产物落 `downloads/`。

**理由**
- 单机自用，重启丢任务记录可以接受（文件不丢）
- 少一层依赖与迁移负担
- 任务历史上限 200 条，超出自动清理已结束的

**代价**
- 重启后看不到历史任务；服务重启期间的任务全部丢失
- 未来若要多用户/持久化，需要引入存储层（`TaskManager` 已是唯一状态源，替换成本可控）

## D8. 「多策略重试」而不是重试一次

**背景**
实测网络到部分 CDN 极不稳定（`SSL: UNEXPECTED_EOF`、分片被重置），
同一个视频有时成功有时失败。

**决策**
失败后按 4 级策略降级重试，每次之间有退避等待：
1. 原始配置
2. 等 5s → 换编码偏好
3. 等 10s → 降并发 + 分片下载
4. 等 15s → 单连接 + 更小分片

同时**永久性错误直接失败**（404/不支持/需登录/地区限制），不浪费时间与流量。

**理由**
抖动的特点是"换个时刻就好"，零间隔连打三次等于撞同一时刻。
实测退避后成功率明显改善。

**代价**
- 失败反馈变慢（最坏 ~30s 退避 + 4 次尝试）
- 需要防误报（见 D9）

## D9. 严格判定「完成」而不是乐观判定

**背景**
开发中发现两个会**误报成功**的问题：
1. yt-dlp 对播放列表内某个条目失败仍返回退出码 0；
2. 结果文件（`--print-to-file`）是追加写入，跨任务/跨尝试会读到别的任务写的路径。

**决策**
收尾判定（`_finalize`）做三重校验：
- 读回结果文件**全部行**并逐行校验文件真实存在
- 对比播放列表预期条目数与实际产物数
- 结合"放弃重试"计数

不满足则标 `done + incomplete: true`（界面显示「部分完成」），
同时**抖动自愈不误报**：产物数达标就清零失败计数。

**理由**
对下载工具而言，"以为下好了其实没下全"比"报错"危害大得多。

**代价**
判定逻辑复杂度上升（已抽成独立方法并配 5 项单元测试）

## D10. 链接形态纠正与错误中文化

**背景**
用户实测报错：抖音 `/note/` 链接 → `Unsupported URL`；
YouTube → `The page needs to be reloaded.`。两者都不是配置问题。

**决策**
- `normalize_url()`：把已知不支持的形态（抖音 `/note/` → `/video/`）自动改写后重试
- `friendly_error()`：把 14 类引擎报错映射为可操作的中文提示（**保留原始报错**）
- 修复了"错误提取只取最后一行"导致提示被当成错误的 bug

**理由**
用户看到的应该是"我该做什么"，而不是引擎内部术语。
同时原始报错必须保留，否则无法上网搜、无法提 issue。

**代价**
错误映射表需要维护（新增站点报错时补充）

## D11. 自动探测 JS 运行时

**背景**
新版 yt-dlp **默认只启用 deno**。用户机器装的是 node，未显式声明，
导致 YouTube 的 n 挑战解不开，报 `The page needs to be reloaded.`
（实测：0 个画质 → 加 `--js-runtimes node` 后 80 个画质）

**决策**
`detect_js_runtime()` 按 node → deno → bun → qjs 顺序探测，
自动注入 `--js-runtimes`；探测不到时自动跳过（不影响其它站点），
并在 `/api/health` 暴露状态、启动自检里提示。

**理由**
这是"必须显式配置但用户无从知晓"的典型陷阱，让用户手动加参数不可接受。

**代价**
- 依赖 PATH 里有 node；未安装时 YouTube 画质会残缺（已给明确提示）
- 若用户有多个运行时，选择顺序固定（node 优先）

## D12. 前端零构建依赖与自研 store

**决策**
前端用 Vue 3 + Vite，但**不引入** Pinia/Vuex/UI 组件库/Tailwind，
store 用 `reactive` 自研（约 380 行），样式用原生 CSS + 设计令牌。

**理由**
- 依赖越少，`npm install` 失败面越小（网络受限环境很重要）
- 界面是定制的霓虹 HUD 风格，通用组件库反而要大量覆盖样式
- store 需求简单（状态映射 + SSE 订阅管理），自研更直白

**代价**
- 缺少开发工具链辅助（Vue Devtools 里 store 不可见）
- 组件复用性不如引入组件库

---

## D13. 界面风格：暗色霓虹终端 / HUD

**背景**
需求明确要求"前端页面需要足够独特，不要千篇一律"。

**决策**
采用 `cyberpunk-ui` 风格方向并自定义配色（不用工具默认的浅色 SaaS 配色）：
不对称三栏、命令行风格输入框、ASCII 块状进度条、扫描线、等宽字体，
同时满足无障碍硬指标（对比度 ≥4.5:1、可见焦点环、`prefers-reduced-motion` 降级、
全键盘可操作、44px 触控目标）。

**理由**
- 工具类产品适合"控制台/HUD"隐喻，信息密度高且辨识度强
- 避开"导航栏 + 卡片网格"的模板脸

**代价**
- 深色 + 霓虹对可读性有风险，需要用对比度约束兜住
- 扫描线等视觉效果提供开关，照顾不同偏好

## 未采纳的方案（及原因）

| 方案 | 未采纳原因 |
|---|---|
| 直接 `pip install yt-dlp` 到系统 Python | 系统 Python 3.9 不满足 yt-dlp 的 ≥3.10 |
| 用 `yt-dlp` 官方单文件二进制 | 本网络 GitHub Release 不可达 |
| 用 `import yt_dlp` 当库调用 | 版本升级会牵动业务代码；进程调用更易排障 |
| FastAPI + uvicorn | 需要装包，环境风险与依赖成本不划算 |
| 引入数据库存任务 | 单机自用场景收益低，重启丢记录可接受（文件不丢） |
| 用 WebSocket 推进度 | 单向场景过重；SSE 原生够用 |
| 前端上 Tailwind/组件库 | 定制风格下样式覆盖成本 > 收益；依赖面变大 |
| 用 `--print` 拿产物路径 | 会抑制进度输出（实测），改用 `--print-to-file` |
| 直接重试同一命令 | 抖动是时间相关的，零间隔连打会撞同一时刻（见 D8） |
